# Presentation persistence boundary

The experimental bridge uses the Rust SQLite transaction to read personal presentation blocks and save against the complete ordered baseline, metadata and revision. Non-slide blocks remain intact; shared pages, inaccessible attachment owners, remapped IDs and conflicts are rejected. A failed or uncertain save invalidates the session and requires a new read. An application integration exists behind disabled experimental build flags; its presence is not release approval. The integration tests use copied synthetic v11 databases.

An explicit single-slide deletion captures a source-compatible version plus a native recovery record in the same transaction. A later session can list and restore that record while the page, revision, metadata, ordered block baseline and attachment ownership remain valid. Reordering and deletion must be saved separately, and deletion refuses nonempty or malformed separate block properties. The recovery record is an experimental native addition, not the original Windows history format. The resulting restore is limited to a page whose remaining block order is unchanged; media file existence is not checked and no attachment file is deleted. Tests for this path await Apple execution.

Loading/saving media bytes, live collaboration, permissions for shared workspaces, full history parity and exports remain unimplemented. The caller must hold appropriate database security-scoped access across the whole workflow and must not enable UI writes before Apple integration tests and further security review.
