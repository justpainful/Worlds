# Worlds Identity

`WorldsIdentityClient` implements email challenge and verification, PKCE code exchange, device-bound Ed25519 refresh, access token caching, authenticated JSON requests, and remote logout. A single Keychain item holds the refresh token, device ID, user ID and signing seed. Access tokens are held in memory. Refresh is shared inside one client actor and a successful rotation is saved before it is returned.

The server expects `worlds-refresh.v1:<deviceId>:<epoch milliseconds>:<lowercase SHA-256 token hex>`, signed as raw Ed25519 and encoded as unpadded base64url. Its passkey web page currently only accepts a loopback HTTP redirect. `PKCE` supplies verifier, challenge and state, and `exchange` validates state for a browser callback. The native `ApplePasskeyAuthorization` performs a platform assertion and `completePasskey` exchanges a server-issued code with an in-memory PKCE verifier. Browser opening and a loopback listener are not implemented. Native passkeys require the app associated-domain entitlement and an apple-app-site-association file for the server RP ID. The service must accept the actual Apple assertion origin as its configured expected origin. These settings and the native ceremony have not been verified against a deployed server or signed app, so do not claim passkey sign-in works end to end.

The caller configures the service URL and chooses the device name and platform. HTTPS is required except for localhost, 127.0.0.1 and ::1 development endpoints. Keychain data is scoped to the current device and is not migrated from the Windows credential manager. Each client and process needs independent session ownership: the actor does not coordinate rotation with other client instances or processes. Creating multiple clients for the same Keychain account can cause refresh-token reuse and server revocation. The refresh token is marked in flight in Keychain before sending. After interruption or an uncertain response it is never replayed, including after app restart. If the server rotates a token but network delivery or Keychain persistence fails, the original token may be unusable. Recovery requires signing in again; do not silently replay it.

The module is included in SwiftPM and its isolated macOS tests passed in Actions run 42387357673. They use an injected fake transport and in-memory secret store; they do not establish Keychain entitlements, browser callbacks, production service health or device behavior. An iOS-only compile issue was fixed later and awaits another run.


`ApplePasskeyAuthorization` now cancels an active system request when its Swift task is cancelled and ignores callbacks from an older authorization controller. The pre-presentation cancellation test requires no user interaction. Separate synthetic tests cover reopening a saved device session and refusing replay after an interrupted refresh. These additions await Apple CI and do not establish actual passkey, keychain or device behavior. Apple documents cancellation callbacks at https://developer.apple.com/documentation/authenticationservices/asauthorizationcontroller/cancel().
