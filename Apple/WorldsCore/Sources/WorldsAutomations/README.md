# Worlds automations audit and native module

The original scheduler is `src-tauri/src/automations.rs`. Each schedule tick finds enabled due automations, advances the next fire time, and either runs once within the grace window or creates a skipped run. Default grace is 30 minutes, and the boundary is inclusive. A once trigger disables after firing. The scheduler starts three seconds after the process starts and polls every 15 seconds. It is an in-process task, not a server scheduler.

The runner snapshots the source page and records a version, optionally invokes Claude against the snapshot without tools, then prepares a Discord send or edit. `policy.unattended` or explicit authorization for a manual run permits delivery; otherwise it stores a pending action and marks the run waiting. `src-tauri/src/discord/mod.rs` resolves pending actions: decline marks the run cancelled, successful delivery marks it succeeded, and failed delivery records failure. MCP requests queue actions for approval. The Discord bridge in `src-tauri/src/discord/bridge.rs` uses an SSH tunnel to a local service on the bot host. Bot credentials remain on that host. These behaviors are source findings, not a claim of observed live delivery.

Collaboration notifications are a separate system. `services/sync/src/inbox.ts` stores mention and reply notifications in a per-user Durable Object. `src/sync/manager.ts` polls the feed and marks it read using the sync service. They are not equivalent to operating-system push notifications and are not supplied by this module.

`WorldsAutomations` implements Codable trigger, policy, spec, run and approval models, next-run calculations with local calendar and DST handling, offline grace classification, and read-only SQLite access to original automation, run and pending-action rows. The fixture derives from an original schema v11 test database. The read-only repository itself makes no writes or deliveries. The local repository has no account or workspace authorization layer: do not expose it to real shared-workspace data until the original authorization model and account scoping are integrated. JSON numbers beyond signed 64-bit precision may not round-trip exactly. Unknown JSON keys in the spec's structured fields are not preserved by the typed top-level models.

`nextRun` aims to mirror the original: strictly after the input time, Sunday equals zero, invalid clock strings use 09:00, monthly days clamp to month end, nonexistent local times are skipped and the earlier occurrence of a repeated time is chosen. Apple calendar and timezone behavior needs verification against the Rust implementation on supported systems. `disposition` reproduces the 30-minute default comparison; it does not execute, schedule, or persist runs.

iOS and iPadOS do not promise exact arbitrary recurring background execution. BackgroundTasks are system scheduled and cannot be used as a guarantee that a due Discord action will execute on time. A reliable parity solution needs a compatible external scheduler or clearly exposed limits and user consent. There is no Apple Discord bridge, approval delivery, background scheduler registration, AI transform, notification feed client or push delivery in this module. Do not enable unattended sends or mark automations complete from these models alone.

The module and its test fixture are included in SwiftPM. Five tests passed on macOS in Actions run 42389924247; the scheduler and approval workflows remain unverified.

## Experimental foreground scheduler

`NativeAutomationStore` uses new RustStore operations to scan due personal-page automations and atomically claim a due occurrence. The transaction checks the stored due time, page authorization, existing run, supported policy and action, then advances the schedule and creates either a missed `skipped` run or an original-format `waiting` run, source snapshot and pending Discord approval. It never sends Discord, performs a Claude transform or executes unattended actions. Unsupported configurations remain due and are reported as issues. Decline is implemented transactionally for a pending automation action on a personal page. Approval and external delivery remain unavailable.

`ForegroundAutomationScheduler` is explicitly started by a host, waits three seconds and polls every 15 seconds. The host must stop it when inactive. Stopping cannot reverse a SQLite transaction already in flight. It does not use BackgroundTasks or promise execution while the app is suspended. Every scan and claim rechecks the current database; two callers cannot claim the same occurrence because the SQLite immediate transaction advances the due time atomically. A restart loads due rows again. Existing unsupported, malformed or shared-page items are left untouched. This is a narrow implementation and needs full permission, lifecycle and visual review before integration.

The Rust tests use isolated original-schema v11 fixtures and cover duplicate claims, concurrency, missed grace, rejection of shared/unattended/Claude configurations, restart and decline. They ran locally on Windows. `NativeAutomationDriverTests` exercises the FFI path on isolated fixtures but has not run on Apple. SwiftPM must add the `WorldsRustStore` dependency and link the generated XCFramework for this driver. Never enable this scheduler in the application until Apple CI and security review pass.

## Experimental local-copy review interface

`personalSnapshot()` reads summaries, run statuses and owned automation requests in one read transaction. It checks the source page is personal and rejects duplicate JSON keys in page metadata, automation spec and request payload. Requests must match their waiting run, automation and source page. It deliberately omits message content and does not expose the unrestricted legacy repository methods to the interface. The DEBUG-only local-copy view can decline a matching request using the Rust transaction, but cannot approve or send, execute a run, schedule work, create or edit an automation.

The view binds to the independent copy and database identity recorded at opening and checks it before and after operations. These checks detect an ordinary replacement, not a hostile swap and swap-back by a process with the same container access. A failed decline response is unconfirmed and must be refreshed. The view is disabled unless `WORLDS_EXPERIMENTAL_AUTOMATIONS` is explicitly set in a DEBUG build. This remains unverified on Apple until the new Swift and UI tests run; it is not a complete automation implementation.
