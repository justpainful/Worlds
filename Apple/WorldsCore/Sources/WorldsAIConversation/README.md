# Experimental native conversation coordinator

`ConversationCoordinator` accepts a caller-chosen run UUID, emits `onAccepted` only after the user message SQLite transaction commits and before launching `ClaudeRunner`, forwards parsed text and tool events, and stores the final assistant response and `sessionOk`/`isError` metadata before reporting success. Unexpected tool events cause an error and are recorded as steps. MCP is always nil; no tool execution or approval is authorized by this module. This relies on a trusted Claude executable respecting the existing runner's disabled-tool arguments. Recording an unexpected tool call after the event cannot undo an action by an untrusted executable.

`SQLiteConversationStore` writes the original schema 11 `ai_chats` and `ai_messages` tables in transactions, preserves step status including null, orders stored messages by timestamp and rowid, and resumes only after a prior successful assistant result. It accepts only page-free chats created by that same store instance; it refuses existing chats after app restart or from other store instances. This is not a complete authorization boundary: existing chat metadata or an existing Claude session may contain page or attachment context, even when `page_id` is null. It must not access user databases before account, context and attachment authorization is implemented. Chat title normalization, operation history, activity aggregation, referenced chats, page and block context, attachments, user instructions, approvals, and reconciliation of unfinished runs remain unimplemented.

One store instance prevents simultaneous runs for the same chat and refuses duplicate native run IDs. Other store instances cannot open a chat created by it; direct writers and legacy clients do not follow this policy. Reopening conversations after restart, cross-process cooperation with existing clients, process-tree termination, persistent recovery after a crash, and precise stream delivery ordering to an asynchronous UI remain unresolved. A cancellation before launch can leave the user message and a failure result; a failed result save propagates and retains the in-process reservation. The caller must not report a result as saved until `run` returns successfully. The acknowledgement means SQLite commit with synchronous FULL, subject to operating-system and filesystem guarantees; acknowledgement recovery after process restart is not implemented. There is no integration with product views. iOS and iPadOS cannot run the local CLI; a real remote backend has not been designed or authorized.

All tests use synthetic SQLite databases and runners. They are written but have not been run on Apple. No Claude credentials, user database, MCP server or network service was accessed. The module is experimental and must remain disconnected from the app until the missing concurrency and authorization work is completed.

Assistant finalization checks that the run ID matches the accepted run and chat before writing or releasing a reservation. The coordinator bounds events to 20,000, accumulated text to 8 MiB and tool names to 512 bytes each and 1 MiB total. It does not forward tool input because no tools are authorized. On the first limit violation it asks the runner to cancel and records a bounded failure. The injected runner must still respect cancellation: a malicious or stuck runner can ignore the request, and process-tree shutdown is not guaranteed. The new cases have not run on Apple yet.
