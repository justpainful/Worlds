Snapshot: 2026-11-08. The original checkout was at `185ee9a1019c8b7bc685d22dabf1b699579189cc`. The storage, account and sync paths cited below had no tracked local modifications at inspection time. The Apple worktree was at `5449ec3c32f40d6b9f3f2534a0858cf3538bf4e2` and contained uncommitted changes, notably in the Rust store and Swift collaboration store. Those changes are described as working-tree code, not as a published build.

This is a **scoped trace**, not the complete Worlds feature inventory. It contains 20 independently checkable requirements drawn from actual code paths, not 20 product features. Rows overlap and have different sizes. Source inspection means the implementation was read, not that it was run. Test names are pointers to test code, not claims of passing. `Partial` includes code that is disconnected, limited to a fixture, or lacks Apple/device/service verification. None of these rows has evidence for all three platform acceptance gates; therefore zero can be marked complete against the acceptance criteria here. This is not a percentage for the overall Apple objective.

For every row, acceptance means: preserve the source's data contract and permissions, connect a real native workflow on iPhone, iPad and Mac where applicable, pass the listed positive and negative scenarios on Apple, and record the resulting CI run and visual/device evidence. Platform-specific restrictions must be resolved, not hidden. Real user data and production services are not test fixtures.

## Evidence limits and next audit work

The inventory does not yet cover every database column, migration branch, identity route, MCP operation or sync-service endpoint. It does not merge uncommitted original drawing work into the Apple branch. Tests and CI results must be recorded per run and commit separately from this source trace. In particular, a passing component test or isolated harness does not prove a production workflow, a physical device installation, visual parity, or complete feature transfer.

The remaining audit must enumerate each source branch and relevant original local change, bind each acceptance criterion to actual test results, and reconcile this scoped inventory with the rest of `FEATURE_PARITY_MATRIX.md` without double-counting overlapping requirements.
