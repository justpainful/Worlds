# Personal video playback integration status

The original file resource stores an attachment ID in `metadata.file.attachmentId` and looks up its physical file beneath the sibling `attachments` directory. `WorldsDatabase.personalFileAttachment` checks the live file page, its personal workspace and the matching attachment ID in one read transaction. `AttachmentVault` uses descriptor-relative traversal and refuses symlinks in the attachment path and hard-linked files. These checks do not constitute a continuously enforceable authorization lease: a page may change sharing state later, and external same-user processes can race path changes.

The experimental selector asks the user to select the Worlds directory, keeps its security-scoped access, checks that `worlds.db` matches the session database file identity, and looks up the personal attachment. The descriptor must be passed directly into the player and retained until a bounded private playback copy is made. Reopening the path after checking it is not acceptable. An experimental button is wired behind `WORLDS_EXPERIMENTAL_PERSONAL_VIDEO`, which is not enabled in product builds. The player now consumes the already-open descriptor without reopening the attachment path. The integration still awaits security review and Apple-platform verification. Independent local database copies exclude attachments and are not eligible.

The existing player uses AVFoundation and supports only formats and codecs actually playable on the device, with a 512 MiB private-copy limit. It does not implement HLS links, DASH, external transfer, video editing, export, or streaming large local files. Even `isPlayable` is not proof of successful playback. Apple validation must use a synthetic real video, exercise correct and wrong directories, cancellation, a shared page and mismatched attachment, symlinks, unavailable and unsupported files, playback errors, cleanup and scope lifetime, plus visual checks on iPhone, iPad and Mac.
