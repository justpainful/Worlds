# Personal template instantiation: trace and blocker

Status: investigated, not implemented or enabled in the Apple app. This report describes source behavior and concrete reasons the currently available personal-store bridge cannot safely expose it. It is not a complete inventory of template semantics or proof of original runtime behavior.

## Original execution

* `src/shell/CommandPalette.tsx` calls `api.instantiate(h.pageId)` when a search hit has kind `template`; `src/views/TemplatesView.tsx` and `HomeView.tsx` use the same API. The JS wrapper `src/lib/api.ts` invokes Tauri `template_instantiate`, optionally accepting destination parent and title.
* `src-tauri/src/commands.rs` computes `drawing_copy::Plan::tree` for the complete source tree, requests its authorization, then invokes `store::instantiate_template_authorized` inside a transaction with the resulting permit.
* `src-tauri/src/store/templates.rs` verifies kind, selects `metadata.templateResourceKind` or `page`, deep-copies the template subtree using `duplicate_page_authorized`, replaces `{{date}}` in the new root's title and block JSON, clears the template category, adds `fromTemplate`, updates FTS and records a tree change.
* `src-tauri/src/store/pages.rs` recursively visits live descendants in sort order, creates new page and block identities, preserves content/metadata except its explicitly removed keys, and invokes the separate drawing copy path when applicable. File and attachment references require their own source behavior analysis: the ordinary duplication code must not be assumed to create independent attachment bytes merely because it duplicates a block.
* `src-tauri/src/drawing_copy.rs` builds and authorizes a tree copy plan, including drawing scenes and original assets. Authorization and plan freshness are part of the operation, not UI decoration.

## Apple blocker

`Apple/RustStore` reuses much of the original `store`, but its `drawing_copy::require_current` and `drawing::duplicate_into` deliberately refuse drawing copies. It also substitutes `db::attachments_dir` with a disabled path, and the personal local-copy import intentionally omits attachment files. Its `require_personal` checks one page per call; the existing original recursive duplicate function does not itself call this check for each descendant or verify that referenced pages/assets are personal. Therefore calling `store::instantiate_template` directly, or validating only the top-level template before calling it, would not establish authorization for the entire subtree or destination and could yield broken or unauthorized references. No Swift FFI endpoint exists for template instantiation. No app action is enabled; search labels template results as view-only.

Even for an apparently text-only template, arbitrary nested block JSON and metadata can contain page references, media references, embedded resources, unknown extensions and drawing data. A simple substring scan or silently dropping unrecognized content is not evidence of safe copying. A restricted subset could be offered only with a precise schema and explicit refusal of everything outside it; it would not constitute full template parity. The current task requires preservation, so this investigation does not enable an incomplete clone.

## Concrete path to implementation

1. Define and validate a personal-only source and optional destination, on an independent database copy whose identity and security scope are held for the full operation. Enumerate the complete tree inside the same immediate SQLite transaction; reject ambiguous metadata, shared/workspace/deleted descendants, destination cycles and invalid references. Bound tree depth, node count and input sizes and handle concurrent changes without a time-of-check gap.
2. Trace and reproduce ownership and lifetime rules for every known page, block, attachment, drawing and embedded-resource reference. Preserve unknown fields losslessly or refuse the operation without creating any rows. Implement compatible asset copying and drawing authorization rather than bypassing `drawing_copy` permits; do not present references to unavailable source attachments as an independent copy.
3. Reuse the actual template and duplication implementation only after preconditions and transactional behavior have been demonstrated. Preserve source date replacement, ordering, history/change/FTS updates, generated IDs and error/rollback semantics. Derive local date with the same intended platform behavior and test timezone boundaries.
4. Add isolated schema-v11 integration fixtures for nested pages, title and block tokens, unknown values, attachment-backed media, drawing scenes, malformed and duplicate keys, shared children, malicious destination, conflict/revocation and rollback. Verify no source modification, complete copied payload and indexes, generated identities, no orphan files, and no write on refusal. Include tests of legitimate source behavior instead of assuming a clone must have independent asset bytes.
5. Only after Rust and Swift bridge tests on Apple should the product action be connected to an explicitly identified local copy, with undo/error and restoration behavior and iPhone/iPad/Mac UI validation.

These steps need backend and UI work; no completion or percentage is claimed from this analysis.

## Structural preflight added

`Apple/RustStore/src/template_preflight.rs` now contains an isolated, non-mutating preflight over one SQLite read transaction. It checks the template kind, personal status of every live descendant and destination, rejects a destination inside the source, cycles, ambiguous/shared metadata and bounded-size violations, and reports page/block/attachment-record/drawing counts. Four synthetic schema-v11 tests passed on Windows; they cover nested drawing and attachment records, shared and ambiguous descendants, destination rejection, cycle rejection and byte-for-byte unchanged database. The check is not exposed through FFI or connected to a button, and is explicitly not an authorization permit. It does not yet traverse arbitrary references, validate attachment bytes, acquire drawing permits, copy data, or keep its read snapshot across a later write. Any future operation must recheck within its write transaction and complete the gaps above. Apple builds and platform-specific behavior remain unverified.

## Reference checks in development

An additional, unexported `inspect_known_references` function checks known attachment IDs in JSON, project links, page mentions and indexed `refs`. It requires each referenced page to be personal and each referenced attachment owner to belong to the template tree; it also verifies each owned attachment record using confined no-follow file opening, regular-file size and, on Unix, single-link checks. The current drawing-copy authorization is unavailable, so drawing pages fail closed. Checks execute without writes in a single SQLite read snapshot, and seven targeted Rust tests passed on Windows, including shared page, missing/foreign attachment, drawing refusal and unchanged data. On Windows, confined filesystem open deliberately fails closed, so these results do not validate successful attachment access; actual Apple no-follow, symlink, hard-link and file-lifetime tests are still required.

This is a partial detector, not a permit: arbitrary extensions can hide references under unrecognized keys, and validation cannot keep files or authorization valid after the snapshot/descriptor is released. It does not perform a write or copy. A future copy operation must re-run all checks inside its own immediate write transaction and retain verified file handles through safe staging, implement drawing permits, and fail closed on unhandled formats. The product action remains disabled.
